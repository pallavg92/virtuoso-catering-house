## TOP OPEN QUESTION: Static-asset Cache-Control on Hostinger

**Confirmed, independent of any single PSI run.** Direct `curl -I` against 7 static asset types (bundle.css, main.js, robots.txt, a .webp image, a .woff2 font, favicon.svg, the menu PDF) shows **zero `Cache-Control` header and no `ETag`** on every one, while every Express-rendered HTML route (`/`, `/sitemap.xml`, blog posts, landing pages, the 404 page) correctly carries `x-powered-by: Express`, an `ETag`, and `Cache-Control: public, max-age=0, must-revalidate`. Static responses never carry `x-powered-by: Express`. This matches the coordinator's own missing-file test (a nonexistent CSS path returns the Express-rendered 404; a real CSS file returns neither Express header) — proof the edge serves existing files itself and only proxies to Node when no static match exists. **Verdict: `server.js`'s `express.static` `setHeaders` block is correct code that cannot execute in production**, because Node is never invoked for these requests.

On whether PSI's "Use efficient cache lifetimes" audit is still triggering: my own PSI run today (`pagespeed_check.py`, mobile) scored it 0 with **"Est savings of 746 KiB"** across **24 first-party resources, all at `cacheLifetimeMs: 0`** — named items include `hero-candlelit-florals.webp` (104,065 B), `virtuoso-catering-house-weddings-service.webp` (90,869 B), `virtuoso-catering-house-bespoke-menus-service.webp` (90,763 B). The coordinator's later run didn't surface this insight — that is Lighthouse's per-run insight-selection threshold varying, not the underlying condition changing; the header-level evidence above is deterministic HTTP behavior, not a simulated trace, and it hasn't changed. Treat the 746 KiB PSI number as noisy; treat "zero Cache-Control on every static asset" as fact.

**What I could not verify (no hPanel/SSH access):** which web server actually terminates behind the `hcdn` edge. Every response — static, dynamic, even bare 301 redirects — carries `server: hcdn`, `platform: hostinger`, `panel: hpanel`; Hostinger appears to strip/replace the real `Server` header, so Apache vs. LiteSpeed vs. nginx cannot be determined from outside. I also could not confirm `AllowOverride` status for `public/`, or whether hPanel exposes a CDN/cache-TTL control, or test-deploy anything myself.

**Recommendation, ranked, both cheap enough to try in parallel this week:**
1. **Check hPanel first** for a CDN/Speed/Cache section with a static-asset TTL setting. The `hcdn`/`platform`/`panel` headers on literally every response (including the 301s) prove a Hostinger-operated edge unconditionally wraps this domain — that class of product commonly exposes its own cache-lifetime control independent of origin headers, which would work regardless of the underlying server software.
2. **In parallel, add `public/.htaccess`** (not `dist/.htaccess` — `dist/` is not served) with the same `mod_headers`/`mod_expires` block already proven in `dist/.htaccess`. Zero risk: if unhonoured, nothing changes; if honoured, it fixes this immediately. Hostinger's shared/business tier has historically run LiteSpeed, which ships an Apache-compatibility mode that generally *does* read `.htaccess` `mod_headers`/`mod_expires` directives — plausible but **unconfirmed**, must be tested empirically.
3. **Verify with the exact command already used in this audit**: `curl -sI https://www.virtuosocatering.com/css/bundle.css` — a `cache-control` line appearing is the pass condition.
4. **Do not** swap `express.static` for a hand-written Express route. It cannot help: the edge intercepts matched static paths before Node is invoked at all (the coordinator's missing-file test proves this) — the problem is upstream of Express, so no Express-side code change reaches it.
5. If (1) and (2) both fail: this is a Hostinger support ticket, not a repo fix — ask specifically whether static files under the app's `public/` are served by their edge/origin independent of the Node process, and how to set response headers on that path.

## Security Headers — confirmed absent, as expected

`server.js` deliberately holds these back (commit 1e68346, recoverable via `git show 8f47f5b -- server.js`). Confirmed absent by direct header inspection across 8+ URL/response types (homepage, sitemap.xml, 404, blog post, landing page, team page, both redirect hops): **no `Strict-Transport-Security`, no `X-Content-Type-Options`, no `X-Frame-Options`, no `Referrer-Policy`, no `Permissions-Policy`.** The only security-adjacent header present anywhere is `content-security-policy: upgrade-insecure-requests` — this is edge-injected by Hostinger (present even on 301s that never reach Express), not app-set, and only upgrades HTTP subresources to HTTPS; it restricts nothing. Independently corroborated by Lighthouse's own audits in today's PSI run: `has-hsts` = "No HSTS header found" (High), `clickjacking-mitigation` = "No frame control policy found" (High), `csp-xss` = "`script-src` directive is missing" + "`object-src`... missing" (High), `origin-isolation` = "No COOP header found" (High). Not a regression — this is the documented, deliberate current state pending an HSTS decision.

## Regressions / New Issues Found

**No regressions in the three headline fixes.** Sitemap: 39 `<loc>`, 22 `<lastmod>`, 12 distinct dates, all traceable to `page.post.updated||date` in `pageMeta.js` — logic is clean, the 17 pages without `lastmod` are pages with no post-date field (expected, not a bug). Images: 26 `<picture>` on homepage, 0 unsized `<img>`, `fetchpriority="high"` present on the hero — matches the commit's claims exactly. `/team/aarti-sharma`: 200, self-canonical, `Person @id` resolves cleanly, no more dangling 404 reference from `/about`'s schema, both LinkedIn and Instagram `sameAs` present, indexable (no noindex).

**One real, live markup defect, newly reaching production today:** `scripts/html-post.js`'s webp-sibling check (`src.replace(/\.(jpe?g|png)$/i, '.webp')`) doesn't exclude `.svg`. For an SVG, the replace is a no-op, so `hasWebp()` checks for the SVG's own filename and trivially finds it "existing" — wrapping it in `<picture><source type="image/webp">` pointing at the same `.svg` file. Confirmed live right now on `/services` (`virtuoso-catering-house-services-hero.svg`) and `/blog` (`virtuoso-catering-house-journal-hero.svg`). Effect is cosmetic-only (browsers decode by the real served `Content-Type`, not the `type` hint, so the image still renders), but it's invalid, misleading markup and a pointless no-op wrapper. This logic bug predates today (present in the dead `dist/` build too) but is live on the actual domain for the first time now that Express calls `processHtml` per response. Low/Medium priority fix: exclude `.svg` from the webp-sibling check.

**Redirect chain (new finding, not previously checked):** `http://virtuosocatering.com/` takes 2 hops to land on the canonical URL (apex-http -> apex-https [edge-level, no Express header] -> www-https [Express hostname middleware]) before 200. `http://www.virtuosocatering.com/` and every legacy WordPress redirect in `utils/redirects.js` (`/gallery`, `/about-us`, `/menu`, `/thank-you`, `/blogs`, etc.) are clean single-hop 301s. Low priority.

**IndexNow:** not implemented (no key file, no submit call anywhere in the repo) — zero-cost win given Search Console API isn't configured.
